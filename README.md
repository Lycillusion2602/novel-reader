# 砚读 · 离线中文小说阅读器

手机上读本地 txt 小说的离线阅读器。纯 HTML/CSS/JS 零框架，用 Capacitor 打包成 APK。
不联网、不上传、不请求任何权限，书全部存在手机本地数据库里。

### 2.1 多宝格书架（数据驱动，可改可扩展）

首页是个圆形博古架，代码在 `www/js/shelf.js`。**结构、格子、里面放什么全是配置，没有写死**：

```js
// 骨架：横板 [x1,y,x2] / 竖撑 [x,y1,y2]，画布 400×400，圆心 (200,200) 内径 168
H: [[38,157,192], ...]
V: [[192,34,157], ...]

// 格子：[左上角 x, y, 宽, 高] + type 决定里面放什么
SLOTS: [
  { x:198, y:46, w:72, h:78, type:'books' },
  ...
]
```

**改结构不用动逻辑**，三种方式任选：

```js
Shelf.configure({ H: [...], V: [...], SLOTS: [...] });   // 运行时改
Shelf.configure({ fillet: 8 });                           // 倒角半径，0 = 硬直角
Shelf.configure({ SLOTS: [...] }, true);                  // 第二个参数 true = 存进 localStorage
Shelf.resetConfig();                                      // 恢复默认
```

**扩展：往格子里放别的东西**（挂件 / 摆件 / 印章 …）。注册一个渲染器，再把格子的 `type` 改掉：

```js
Shelf.register('lantern', function (ctx) {
  // ctx.slot  当前格子 {x,y,w,h,type,...}
  // ctx.items 分到这个格子的内容
  // ctx.bookWidth 当前书脊宽度（书多时会自动压窄）
  return '<circle cx="..." cy="..." r="8" fill="#2E6B4A"/>';   // 返回 SVG 片段
});

Shelf.configure({ SLOTS: [{ x:40, y:40, w:80, h:80, type:'lantern' }] }, true);
```

内置的 `books` 渲染器就是按这个接口写的，可以直接抄。`ornament` 是个摆件占位（小陶罐剪影）。

### 2.2 格子的两件事：容量 和 防穿模

**容量。** 每格能放几本由 `slot.cap` 决定，不写就按「可用宽度 ÷ 书脊宽 17」算。
当前 8 格分别是 4/5/5/3/5/3/2/5，一共 **32 本**。
（书脊 14px 时是 40 本 —— 书变厚就要少放几本，这是同一个天平的两端，`cfg.book.idealW` 一个数说了算。）
加书前会再判一次容量，满了直接拒绝：

```js
SLOTS: [{ id:'s3', x:144, y:164, w:52, h:72, cap:3, type:'books' }]
```

**防穿模。** 用户给的格子坐标只是「大概这块地方」，真正能摆书的范围得贴着木板算
（`fitSlot()`），否则书会陷进板里、盖住竖撑：

| 边 | 算法 |
|---|---|
| 底 | 找 10px 内的横板，书底 = 板面 `y - T/2`，**坐在板上** |
| 顶 | 找 10px 内的横板，书顶最多到 `y + T/2` |
| 左右 | 找 10px 内的竖撑，收到撑的内侧面 `x ± T/2` |

板子必须横向盖住格子 60% 以上才算这块格的边界（只盖住半截的不认）。
改完结构跑一遍自检就能确认没有穿模：

```bash
node tools/check-shelf.js
```

几条约定：

- **书的颜色统一绿色系**（`cfg.greens` 8 个绿），按书名 hash 取，同一本书永远同色
- **书的高低错落按 hash**（`thickLo~thickHi` = 0.80~1.00 倍格高），这是设计上的亮点，别抹平
- 书脊宽默认 17px（`cfg.book.idealW`）；同一格书多时统一压窄，最窄 10px
- 书名 ≤4 字直接写在书脊上，>4 字标序号 ①（详见 4.1.1）
- 摆位存在 `slots` store 里，**书库和书架是分开的**：拿下来的书还在列表里
- 点击书脊 = 打开；**长按 550ms = 从架上拿下**；编辑态点书 = 拿下（带确认）

### 2.3 编辑态怎么设计的（踩过一次：能点的地方太小）

第一版编辑态只有一个 1px 的虚线框，除了框里那一小块，点板子、点缝全都没反应——
用起来像「编辑功能没做」。现在三层保证好点、好看：

| 层 | 内容 | 作用 |
|---|---|---|
| 热区 | 藏在书下面，范围是**格子最初划定的矩形往外扩 5** | 手指点偏一点也算点中这一格 |
| 虚线框 | 贴合后的真实可放范围，绿框=能加 / 灰框=满了 | 一眼看出这块地方能放几本 |
| 角标 | 顶部 `n/m`（10.5px，按 400 画布给） | 容量状态；小于 10 会看不清 |

**空格子里画一个加号**，不然没人知道那块虚线是能点的。

选书面板也改成两段，正好对上「往某格加书 / 从某格拿书」两个动作：

```
这一格的书           2/6      ← 每行右侧「拿下」
书库里还没上架        7 本     ← 每行右侧「放上」
```

编辑条上还有两个批处理：**一键摆满**（书库里的书按格子顺序铺进去，每格不超容量，
先每格一本再补满）和 **清空**（只解摆位，不删书）。升级上来的老用户书架是空的，
有这两个就不用一本本摆了。

### 2.4 首页为什么不再「下面空一大块」

书架是圆的，天生正方形，而手机屏是瘦长的，怎么算都会剩出垂直空白。之前的写法把
svg 钉死在 `min(84vw, 330px)`，还塞在一个 `flex:1` 的区域里居中——390 宽的屏上只画
300px，上下各空 200 多 px，看着就是「没铺满」。

现在：

- `.shelf-canvas` 用 `aspect-ratio: 1/1` + `width:100%` + `max-height:100%`：
  **宽度优先撑满**（390 屏上架子 374px 宽），横屏高度不够时自动缩；
  再给一个 `min-height: 240px` 兜底，防某些 WebView 不认 `aspect-ratio` 时高度塌成 0、架子整个消失。
- 舞台 `justify-content: center`，把「架子 + 下面那行提示」**整组**垂直居中，
  上方留白 = 下方留白，看着像有意留的。
- 删掉了原来那块独立空状态：它跟提示行说的是同一件事，还占掉半屏。

## 3. 操作说明

### 3.1 手机实测（不打包）

```bash
node server.js
```

终端会打印局域网 IP，手机连同一 WiFi 后浏览器访问 `http://<IP>:8645` 即可。

**在电脑上先看效果 / 验交互**（不用装 APK，也不用真机）：

```bash
node tools/build-phone-sim.js     # 从 www/index.html 生成 design/phone-sim.html
```

`design/phone-sim.html` 是真页面的副本（数据库换成假数据、打上 `html.native` 模拟安卓），
参数都走 URL：

| 参数 | 作用 |
|---|---|
| `?n=30&on=5` | 书库 30 本、架上摆 5 本 |
| `?chaps=500&para=80` | 每本 500 章、每章 80 段（测阅读性能） |
| `?edit=1` | 直接进编辑态 |
| `?roster=1` | 直接开花名册 |
| `?page=list` | 直接进列表页 |

| `?noread=1` | 假数据全给零进度（没有"继续阅读"卡片的场景） |

配合无头浏览器截图就能自查排版（headless 会忽略 `--window-size`，所以套一层固定
390×844 的 iframe 来钉死手机尺寸）：

```bash
msedge --headless=new --disable-gpu --hide-scrollbars \
  --screenshot=out.png --window-size=420,880 \
  "file:///.../design/_frame.html?p=n%3D12%26on%3D5"
```

`_sim-driver.js` 里还带脚本化的点击流程，会用 `--dump-dom` 把每一步的结果吐出来：

| `?act=` | 走一遍什么 |
|---|---|
| `edit` | 点编辑 → 点格子 → 加一本 → 拿下一本（每步都断言） |
| `fill` | 一键摆满（可配 `n=45` 试超容量边界） |
| `read` | 从列表点一本书 → 等阅读页出来，量耗时/段数/有没有残留遮罩，滚到底看下一章接上没 |
| `roster` | 开花名册 → 数行数 → 点一行确认能进阅读器 |
| `dbg` | 长按「砚读」看诊断面板弹不弹 |
| `roll` | **连续卷轴八项验收**（详见 4.6）：提前加载了多少 px / 章节号连续无空洞 / 块间没断口 / 上滑接回更早的章 / 全程没重画过 / `<p>` 数量封顶 / **静止时画面不跳** / 退出再打开接得上。跑法带 `&chaps=8&para=25` |
| `rollmanual` | 关掉连续阅读：章末挂「下一章」按钮、往下不自动接、点了才接上来 |
| `ui` | **阅读页 UI 六项验收**（详见 4.9 / 4.10）：顶栏底栏长什么样 / **收放两条栏时正文 padding 与字都不许动** / 夜间一键切黑且主题挂到 html 上 / 拖进度条跳章 / 「更多」有提示 / 无报错 |
| `light` | **亮度面板六项验收**（详见 4.11）：弹的是不是这个面板 / 两个太阳 + 滑条三部件 / 跟随系统那行 / 拖滑条遮罩跟着变且滑块落在激活段末端 / 拨开关后压暗撤掉且滑条不给拖 / 无报错 |
| `set` | **阅读设置面板七项验收**（详见 4.12）：弹的是不是新面板 / 字号能加减 + 换字体 / 背景色块与选中态 / 翻页四按钮 / **四种翻页各自的行为**（上下采样 1 个值、平滑 12 个值、覆盖/仿真挂的是那对浮层且浮层里只有几十个段）/ 第四行两个键 / 无报错。跑法带 `&chaps=12&para=25` |
| `reopen` | **「切完翻页方式 → 退回书架 → 再打开」会不会卡死**（详见 4.12 那条教训）：四种方式各来一遍，每次都量「遮罩收掉耗了几毫秒」，超 12 秒判卡死；收尾还查有没有残留浮层 / 残留 block 动画。跑法带 `&chaps=8&para=25` |
| `toc` | **目录面板七项验收**（详见 4.13）：面板宽占屏 70~80% / 右圆角 / 半透明遮罩 / 书名+副信息+倒序键 / 行格式「第X章：名」/ 当前章三重高亮 / 胶囊滚动条（箭头翻屏、拖滑块跳位）/ 倒序真的反过来 / 点某章能跳。跑法带 `&chaps=60&para=25&tname=1` |

## 4. 实现要点

### 4.1 为什么必须分章（以及"一章多大"这件事）

3 MB 的小说整本塞进 DOM 会让手机卡死几秒。做法是导入时按章切分，
每章单独存一条数据库记录，**DOM 里只留当前章前后的几章**（见 4.6 的连续卷轴）。
所以目录和总进度靠 `books.toc` 里的 `{标题, 字数}` 数组算，不读正文。

**但只切章还不够。** 第一版只在"一个章回标题都没认出来"时才按字数硬切，
结果遇到网文合集那种「只有一两个卷标题、中间夹几十万字」的文件时，
**"一章"就是整本** —— 读的时候一次往 DOM 里塞几万个 `<p>`，老 WebView 的排版线程直接瘫掉，
表现是「点进去就卡死、什么都点不动」。现在两道闸：

1. **导入时**：切完章再查一遍，单章 > 8000 字就按 3000 字再切小节，
   标题变成「第一卷 风起 · 3」。实测 25 万字、只有两个卷标题的文件：2 章 → 84 章，单章最长 3059 字。
2. **渲染时**：正文**增量渲染** —— 一次只建 160 段的 DOM（`CHUNK`），
   参考线下方不足 1000px 就再补一批；再加上连续卷轴那套
   （DOM 里最多 5 块、离得远的整块卸掉），不管库里存着多离谱的老数据，
   DOM 里永远只有几百段。目录同理：超过 600 章只画当前章前后各 200 条 + 上一批/下一批。

**遮罩必须有下限。** `showLoading(txt, ms)` 带看门狗（默认 20s，打开书 8s），
到点自己收掉并提示；`window.onerror` 也会收。不然任何一步卡住不回，
那块全屏遮罩就把人锁在界面里了 —— 用户看到的就是"卡死、无法操作"。

### 4.1.1 书脊上写什么（书名 vs 序号）

竖排长书名在 15px 宽的书脊上根本没法看。规则：

- 书名先洗掉书名号/括号再数字数（《三体》算 2 个字）→ **≤4 字：完整竖排写在书脊上**
- **>4 字：不写字，标带圈序号 ①**（超过 20 用 `[21]`，字号自动缩到塞得下）
- 编号**只在需要编号的书里连续排**（第一本标号书就是 ①，中间不断号），按导入时间排序
- 对照表记在「花名册」里：架子下面的入口 → 底部抽屉，列出 序号 / 书名 / 阅读进度，点一行直接读

画在书脊上和列在册子里的符号必须是同一套，所以 `circled()` / `cleanTitle()` /
`needsNumber()` 都放在 `shelf.js` 里 export 出来，`app.js` 直接用，不另写一份。
编号是**每次渲染现算**的（不落库），所以以后加新书导致后面挪号，屏幕和册子也永远对得上。

**待定：册子要不要"实体化"。** 现在的入口是架子下面一个「花名册」胶囊按钮（→ 底部抽屉）。
设想里是在架子前放一张矮几、上面摊一本册子，30° 俯视能看到封面和书脊——
`design/roster-design.html` 出了三个方案（A 立着 / B 摊开 / C 平放），
截图 `design/preview-7-roster-design.png`。**等她选完再落到首页上**，现在不挡事。

### 4.2 编码探测顺序

1. BOM 判断（UTF-8 / UTF-16LE / UTF-16BE）
2. 严格 UTF-8 解码（`fatal: true`），失败说明不是 UTF-8
3. GBK 解码，并统计乱码字符占比，低于 2% 才采纳
4. 兜底：非严格 UTF-8

网上下载的中文 txt 八成是 GBK，第 2 步的 `fatal` 是关键——不加这个参数，
UTF-8 解码永远不会失败，只会吐出一堆 `U+FFFD`，也就是「锟斤拷」。

### 4.3 存储

用 IndexedDB 而不是 localStorage。localStorage 只有 5 MB，一本长篇就撑爆；
IndexedDB 在 Capacitor 的 `https://localhost` 源下没有这个限制，几百 MB 没问题。

| store | keyPath | 内容 |
|---|---|---|
| books | id | 书名、总字数、编码、目录数组 |
| chapters | `bookId:index` | 单章正文 |
| progress | bookId | 当前章、滚动位置、书签 |
| settings | k | 字号、行距、主题、亮度 |
| slots | id | 书架摆位：`{id:'s0', items:['b1','b3']}` |

**书库和书架是两回事。** 所有导入的书都在 `books`（列表页）；
`slots` 只记「哪个格摆了哪几本」。从书架拿下 = 删 `slots` 里的一个 id，书还在；
从列表删除 = 连正文、进度、摆位一起清掉。

### 4.4 安卓状态栏遮挡问题（踩过）

targetSdk 36 会触发 Android 15 的**强制 edge-to-edge**，WebView 铺满整屏，
状态栏和手势条浮在内容之上，标题栏会被状态栏压住。

关键坑：`env(safe-area-inset-top)` 在 **Android WebView 里恒为 0** ——
那是 iOS 的机制，Android 上写了也没用。

解法：JS 检测 `Capacitor.isNativePlatform()`，是原生就给 `<html>` 加 `.native`，
由 CSS 补固定高度（顶部 46px、底部 26px）。浏览器里不加这个 class，不受影响。

补充：光补高度只解决"内容被压住"，不解决**状态栏那一条是白的** ——
那一条得在**原生主题**里把系统栏设成透明 + 给对图标深浅，见 4.10（JS 里那两句千万别加）。

### 4.5 ⚠️ 别用 inset 简写 / aspect-ratio —— 真机的 WebView 比你想的老

**血泪教训。** 首版在真机上同时出了两个"莫名其妙"的毛病，查了半天：

| 症状 | 真因 |
|---|---|
| 页面只占屏幕左边 81% 宽、下面还空一条，「右下大片空白」 | `.page{position:fixed;inset:0}` 里的 `inset` 没生效 |
| 点书架格子什么都没发生（浮层"没弹"） | 选书面板 `.sheet{inset:0}` 同样没生效 |

`inset` 是 **Chrome 87+** 的属性。它一旦不生效，`position:fixed` 就没有任何偏移量，
元素退化成「按内容收缩到刚好包住内容 + 停在原来该在的位置」：

- `.page` 收缩成 330px（正好是里面那个书架 svg 的宽度）、贴在左上角，
  右边和下边就露出 `body` 的底色 `#f5f2ea`——所以看着是"没铺满"。
- `.sheet`（选书面板）是 body 最后的元素，收缩后落在视口**下方**，
  页面又 `overflow:hidden` 滚不到那儿——**面板其实弹了，只是弹在屏幕外**。

而底栏 `.tabbar` 用的是 `left:0;right:0;bottom:0` 分开写的老写法，
所以它是满宽的，对比之下就把那条带衬出来了。

**结论 + 三条规矩：**

1. **所有铺满全屏的地方一律写 `top/right/bottom/left` 四个长属性**，永久别用 `inset` 简写。
   （`.page` / `.sheet` / `.drawer` / `.loading` / `.dim` / 各种 mask，全改了）
2. `aspect-ratio` 是 **Chrome 88+**，老引擎不认会让高度塌成 0（架子整个消失）。
   `app.js` 里的 `ensureSquareCanvas()` 会量一下，塌了就按宽度手动补一个正方形高度，
   转屏时再量一次。改完记得在模拟器里用 `?repro=ar` 验一遍。
3. **国产 ROM 的 WebView 常年不更新**（没有 Play 商店就不升级），
   不要拿"我这台是 Android 15"去推断它支持的 CSS。写新属性前先想一句：
   这个属性是哪个版本加的？降级之后会「只是难看」还是「直接看不见」？
   后者必须给兜底。

顺带：`gap` 用在 flex 里要 **Chrome 84+**；真挂了只是间距变 0（难看但不致命），
目前没动它，等真机诊断面板报出具体版本再说。

**真机诊断面板**：长按书架页左上角「砚读」两个字约 0.8 秒会弹一块黑底绿字的浮层，
打印视口尺寸、`#page-shelf` 实际矩形、`inset` / `aspect-ratio` 的支持情况、
以及完整 UA。让用户截一张图，比来回猜十轮都快。

### 4.6 连续卷轴：把整本书读成一条很长的书页

**旧做法**是「一章一个滚动容器」：读到章尾 → 清屏 → 拉 loading → 把下一章重画一遍。
再快也有一下白屏，而且读完往回翻不上去（上一章已经不在 DOM 里了）。

**现在**：`#chapter-content` 里同时挂着当前章前后若干章，每章是一个 `.chapter-block`
（自带章节标题 + 段落盒子）。滑到哪就在头尾接着补，离得远的卸掉 —— 于是"翻章"这个动作
本身消失了：上一章最后一段和下一章的标题之间**没有断层**，往上也能一路滑回上一章。

三条铁律，少一条画面就会出问题：

| 铁律 | 做法 | 不做的后果 |
|---|---|---|
| 插删内容时视线不许跳 | `preserve()`：记下锚点块的位置变化 d，`scrollTop += d` | 往上加载上一章时，整段字在眼皮底下弹走好几屏 |
| DOM 里的东西要有上限 | `trimBlocks()`：窗口 = 锚点前 1 章 + 后 3 章，最多 5 块 | 一路读下去，`<p>` 涨到几千，老 WebView 排版拖死 |
| 参考线下方永远有现成正文 | `fillDown()` 补段落 + `maybeConnect()` 提前接下一章 | 滑着滑着出现一段空白，再往下突然跳到下一章 |

**"读到 3/4 就接上"是怎么算的。** 参考线（`READ_FRAC = 0.25`，可视区从上往下 1/4 处）
落在哪一块里，就是"正在读哪一章"；`(参考线 − 本章顶端) / 本章估计高度 ≥ PRELOAD_AT(0.75)`
就把下一章 append 进来。章还没画完时高度按「已画高度 × 总段数/已画段数」外推 ——
宁可估短（提前接上）也别估长（漏掉，露出断口）。实测下一章挂上时，
离本章末尾还剩 **1183px**（一章约 3.7k px 时），人滑到章尾时早就接好了。

**往上**：`scrollTop < 2 屏` 且最前面那块不是第一章，就把上一章 `insertBefore` 进来。
给两屏富余是因为这一下要等一次异步查库，贴着顶端触发会在快速上滑时顿一下。

**每章标题跟着自己那一块走。** 以前是滚动容器上挂的一个孤零零的 `<h2 id="chapter-title">`，
一条卷轴里放不下第二个 —— 走到第二章头上就没名字了。现在标题是块的一部分。
块与块之间只留 **3.4em 空白**（不加分隔线：留白比划线更像书，也不打断连贯）。

**进度存的是什么。** 两个偏移要分清，混用会差出一百多像素：

| 名字 | 含义 | 用途 |
|---|---|---|
| `off` | 参考线离本章顶端多远 | 算"这一章读了百分之几" |
| `voff` | **视口顶边**离本章顶端多远 | 存进度 / 存书签 / 恢复位置 |

存 `voff` 是因为恢复时目标章会从"中间某一块"变成"第一块"，章顶端的绝对位置跟着变，
而"视口顶边在章内第几个像素"是纯相对量，跟留白、跟前面挂了几章、跟上下栏收没收起都没关系。
（早先存的是 `off`，恢复出来会往下多走 `ch*0.25 − 顶部留白 ≈ 149px`，实测抓到的。）

**恢复位置是个"要等"的事。** 刚打开时卷轴里只有目标那一章，如果上次读到本章靠后的地方，
可滚动长度不够，浏览器会把 `scrollTop` 夹住（实测夹掉 376px，等于往上弹三段），
而下一章是异步接上来的、接上之后也不会自己回去。所以 `applyPendingTop()` 记一个
"还欠着的目标"，每次卷轴变长就再试一次；手指一碰屏幕就作废（人要自己滑了，不能再拽回去）。

**"下一章"按钮不再等于"重画"。** 自动连读开着时下一章已经在下面挂着了，
点「下一章」就是滚过去（`jumpChapter`），不再把整条卷轴拆了重画；
只有目标章没挂着（目录里跳很远）才退回 `renderStream` 重画。

### 4.6.1 ⚠️ 打开书：为什么以前老是"卡在正在排版正文"，以及根治办法

`openBook()` 里遮罩上的字是一步一步换的（`打开中 → 正在读目录… → 正在排版正文…`），
这不是花活 —— 真机上卡住时，那几个字直接指出卡在哪一步。

#### 根子上的错：让"打开书"去等"排版"

老做法是：`renderStream()` 里**先把本章排到上次读到的位置那么长，才去定位、才收遮罩**。
于是打开一本书的耗时**正比于上次读得多深** —— 读到第 3000 段，就得先建出 3000 个 `<p>`。
真机上这就是几秒到几十秒的假死，期间主线程被独占，**连 `showLoading` 那个 8 秒
看门狗的 `setTimeout` 都排不上队** —— 所以不是"遮罩忘了收"，是兜底代码根本没机会跑。
表现就是永远停在「正在排版正文」，怎么加超时都救不回来。

之前加的 `INIT_CAP`（段数上限）、`INIT_BUDGET`（时间上限）都只是把假死从"几十秒"
压到"几秒"，**没有解决这个前提本身**。

#### 现在的做法：打开不等排版，剩下的后台续排

1. `makeBlock()` 建好头一批段（`CHUNK = 64`）就够撑起一屏多 —— **立刻定位、立刻收遮罩**。
   打开耗时跟"上次读到哪"完全无关（实测 20000 段的天书：**68ms**）。
2. 剩下的交给 `startFill()` 后台续排：**一个时间片只补 `SLICE_N = 24` 段、
   最多占 `SLICE_MS = 8ms`**，片与片之间用 `nextFrame()` 把主线程还回去。
   单个同步块小到不可能卡住。
3. 每补一片就 `applyPendingTop()` 一次 —— 内容变长后位置自动往目标推，
   而参考线上那一行始终不动（看着是内容在下面长出来，不是画面在跳）。
4. **手指一碰就 `stopFill()`** —— 人要读了，不跟他抢主线程。换书/跳章/离开阅读页也停。

#### 配套的几道闸

| 措施 | 挡的是什么 |
|---|---|
| `FILL_MAX = 4000` | 见下面的"失控循环"：没有这道闸，一本没切开的大书会被整章几万段全塞进 DOM |
| `fillDown` 加了 `Date.now() - t0 < 10` | 一帧里补 8 批在真机能把这一帧拖到几百毫秒，滑起来一顿一顿 |
| `nextFrame()` = rAF 与 `setTimeout(50ms)` **赛跑** | `requestAnimationFrame` 在页面不可见时不触发（WebView 被盖住、切后台）。只靠 rAF，续排那一串永远挂在半路 |
| `openBook` 里 `Promise.race(renderStream, 9s)` | 最后一道保险：万一上面全失效，遮罩也必须收掉 |

#### 顺带挖出来的"失控循环"（很值得记）

改成续排之后实测发现：段数和 `scrollTop` **同步线性涨到底**，一本 20000 段的书被
整章排进 DOM（20128 段）。链路是这样的：

```
打开时位置被夹在底部 → 参考线落到最末一块
  → fillDown 补段，把末块往下推
  → preserve() 补偿，scrollTop 跟着涨
  → 视口又贴着底，参考线还是不够长 → 再补 ……
```

三处一起修才好：

1. `applyPendingTop` 的"到位"判定必须是 `Math.abs(scrollTop - want) <= 2`。
   写成 `scrollTop >= want - 2` 的话，**被夹到比目标更大时也成立**，会把"还没到位"误判成"到了"。
2. "用户是不是自己滑走了"只认**往上退**（`scrollTop < lastTop - 40`）。
   往下多出来往往是补段把视口带下去的，判成"人动了"会把欠着的目标误伤掉，位置再也回不去。
3. `fillDown` 加总量上限 `FILL_MAX`。

修完同一本书：**遮罩 68ms 收掉、DOM 只留 2152 段、位置精确落在 300056（目标 300000）**。

#### 恢复阅读位置：存「哪一章 + 章内偏移」，别存绝对 `scrollTop`

`state.pendingWant = { blk, voff }`，每次卷轴变长都**按当前几何重算**要落到哪儿
（`applyPendingTop`）。存绝对值有两个坑，都是实测踩出来的：

1. 后来插进来一章（往上接），同一个 `scrollTop` 就指到别处去了（差整整一章的高度）；
2. 长度不够时目标被浏览器夹住，而"被夹过的值"会被当成目标反复落位，
   于是**重开永远差那么几段**（`?act=roll` 第 8 条就是这么红的）。

另外还记了一个 `lastTop`：如果当前位置已经不是我们上次落下的地方了，说明是
**别的东西**在动它（人滑了、自动翻页推了、跳章了）→ 立刻放弃，别把人拽回去。
"被夹住"不算走掉（那时 `scrollTop` 还是它），所以还会等卷轴接长继续落位。

### 4.7 关了连续阅读会怎样（手动模式）

`state.settings.autoNext` 关掉之后，往下不再自动接：`finishBlock()` 会在每章尾巴挂一块
「本章完 / 下一章 · xxx」胶囊按钮，点一下才把下一章接上来（接上后按钮自己收掉，
换成再下一章的）。**往上接不受这个开关影响** —— 往上能滑回上一章是阅读器的本分，
不该是个开关。另外下一章已经在卷轴里时不会挂按钮（底下明明有字，中间插个按钮
只会让人以为后面没了）。

这一段原来是**写在纸上没落在代码里**的，2026-09-30 那轮才补齐，三处一起：

| 位置 | 之前 | 现在 |
|---|---|---|
| `ensureNeighbors()` | 无条件预取下一章 → 章末按钮挂出来了，下一章的内容又紧贴在你下面，开关按了看不出差别 | 向前那一支只在 `autoNext` 开着时走；向后（上一章）照旧无条件补 |
| `loadChapter()` 接上之后 | 上一章那张「本章完」没人收，成了假话 | `dropStaleEnd(findBlock(idx-1))`：非「全书完」的那张收掉（和 `refreshBlockEnds()` 共用同一个函数） |
| `_sim-driver.js ?act=rollmanual` | 断言写的是 `blocks.length >= 2`，可"没点之前"其实已经挂着两章了 —— 点不点按钮都成立，**假绿把一个 bug 钉成了规格** | 改成 `beforeLen === 1 && afterLen >= 2`，才真的在验"点一下才接上来" |

代价要知道一条：手动模式下点底栏「下一章」，目标章没挂着 → 走 `renderStream` 重画，
会闪一下（这是 4.6 早就定过的退回路径）。章末那张胶囊才是手动模式的正路：
它是 `loadChapter(append)`，接进来不重画。

### 4.8 继续阅读卡片：占了架子下面那块留白

书架天生正方形，手机竖屏下面必然空一截（见 2.4），与其空着不如放最近在读的那本：

```
┃ 三体                                    续读 ›
┃ 读到「第五章 苍穹之用」· 17%
━━━━━━━━━━━━━━━━━━━━━━━━                    ← 底部进度条
```

- **选哪本**：`paintContinue()` 从 `withProgress()` 的结果里挑 `read.at`（最后阅读时间）
  最大的那本；一本都没读过（index 0 且 scrollY 0）就整张 `display:none`，**不留占位**。
- **书脊颜色**跟架上是同一套绿：`Shelf.colorOf(书名)`，同一本书两处颜色永远一致。
- **读完了**显示「已读完 · 点开重读」，进度条 100%。
- 编辑态隐藏（`state.edit`）。
- 点整张卡 = 直接 `openBook(id)`，续读到上次的位置。

三个坑，都是真踩过的：

1. **渲染缓存键必须把卡片用到的字段也算进去。** `shelfKeyOf()` 原来只拼
   「编辑态 / 宽度 / 书数 / id / 摆位」，读了本书之后这些全没变，于是
   书架不重画 —— 首页卡片还指着上一本。现在末尾加了一截
   `/C<id>@<index>@<at>;`，读了新书 key 一定变。
2. **切标签回书架得真的重画。** `bindEvents()` 里原来只有
   `if (p === 'list') renderList();`，书架分支什么都不做，于是「列表页读两章 → 切回书架」
   卡片、副标题、书脊百分比全冻结在离开那一刻。补了 `else renderShelf();`。
3. **`width:100%` 在这会让卡片比架子还宽、顶到屏幕边。** `.shelf-stage` 是
   `flex-direction:column; align-items:center`，此时子元素的百分比宽度是拿
   **容器内容宽度**算的，而内容宽度又被它自己撑大。改用 `align-self: stretch`
   + `margin: 0 26px 4px`，宽度跟着舞台走，不再反向撑大容器。
   （`.cc-go` 还加了 `white-space: nowrap`，免得窄屏把「续读 ›」压成竖条。）

顺带修了进度百分比上不去的问题：`toc[i].len` 是**字数**不是渲染高度，两者不成比例，
只按"读到第几章开头"算会系统性偏低（实测着显示 94% / 63% / 31%，永远不到 100%）。
现在 `withProgress()` 额外按 `scrollY` 估一个章内比例折进去，
`updatePct()` 再加一条：最后一章真的滚到底就直接给 100%，其余情况封顶 99.9%。

### 4.9 阅读页的排布：顶栏 / 正文 / 底栏

```
┌──────────────────────────────────────┐
│ ‹ 返回        书名 · 5/20 · 17%    ⋮ 更多 │   顶栏（浮层，46px + 状态栏留白）
├──────────────────────────────────────┤
│                                      │
│  正文。一条连续的长书页，两边对齐，      │   正文区（只给系统留白让位）
│  行距宽松，段间留白明显。               │
│                                      │
├──────────────────────────────────────┤
│          第 5 章：苍穹之用             │   底栏上段：当前章节标题
│  上一章  ●━━━━━━━━━━━━━━━━━━  下一章   │              章节切换 + 进度条（可拖）
│ ──────────────────────────────────── │
│    ☰ 目录    ☾ 夜间    ☀ 亮度    ⚙ 设置 │   底栏下段：四个带文字的功能键
└──────────────────────────────────────┘
```

- 两条栏都是 `position: absolute` 的**浮层**，用 `var(--panel)`（比正文底色浅一档）
  跟正文区分开，不换别套颜色。
- 底栏那根进度条：轨道 3px，但热区给了 22px 高（3px 手指根本点不准）；
  拖动圆点 = **按章节比例跳章**（跟目录里点一章一个意思），
  拖动过程中只挪圆点，**松手才真的跳** —— 跳一次章要等异步查库，边拖边跳会把库拖垮。
- 「更多」是留给以后扩展的入口，现在按下只给个提示。
- 圆点用 `margin` 居中，不用 `translate(-50%,-50%)`：它挂在 `left` 上，
  再叠 transform 会跟栏自己的位移动画抢合成层，老 WebView 上会"圆点比轨道慢半拍"。

#### ⭐ 收放两条栏：**v-show，不是 v-if**

她拿 Vue 的 v-if / v-show 打比方，要的是后者。

以前栏收起时正文的 `padding` 跟着一起收（44px ↔ 14px），一收一放正文就
"往中间缩"一次 —— 那是真的改了盒模型，等于每次点屏幕都把整章几百个 `<p>`
重排一遍（老 WebView 上肉眼可见地抖一下），而且**视线里那行字会整段移位**。

现在：

```css
/* 正文只给**系统**留白让位，跟栏的高矮无关 */
.reader-body { padding: calc(var(--safeT) + 12px) 20px calc(var(--safeB) + 20px); }
/* 栏自己只是 transform + opacity 切换 */
.bars-off .reader-head { transform: translateY(-100%); opacity: 0; pointer-events: none; }
.bars-off .reader-foot { transform: translateY(100%);  opacity: 0; pointer-events: none; }
/* ⚠️ 没有任何一条 .bars-off .reader-body { padding: ... } —— 加了就前功尽弃 */
```

代价是栏展开时会盖住正文最上/最下一小截（约 160px）。划算：它是临时浮层，
一滚就收，比"每次点屏幕重排一次全章"便宜得多。
验收见 `?act=ui`：收起前后 `padding` 必须一字不差，且参考线上那一段的位移 ≤ 1px。

### 4.10 黑色主题：主题挂到 `<html>` 上，状态栏自己接上

**白边是怎么来的。** 以前主题只挂在 `#page-reader` 上
（`applySettings()` 里 `$('page-reader').setAttribute('data-theme', ...)`），
于是**只有正文变黑**：`html` / `body` 的底色还是纸白，loading 遮罩、
确认弹窗外圈、以及系统状态栏那一条全是白的 —— 黑底上顶一条白边，就是这么来的。

现在进阅读页时把主题**挂到 `<html>`**（`syncTheme()`），离开立刻摘掉
（书架和列表还没做主题适配，挂着会变成半吊子）：

```js
document.documentElement.setAttribute('data-theme', 'dark');
```

**系统状态栏**：透明这件事**交给原生主题**，JS 只管图标深浅。

```xml

<item name="android:statusBarColor">@android:color/transparent</item>
<item name="android:navigationBarColor">@android:color/transparent</item>

```

```js
// JS 这边只调 setStyle，而且 typeof 判过再调、还接了 .catch()
SB.setStyle({ style: dark ? 'LIGHT' : 'DARK' });
// Style 的命名反直觉：LIGHT = 图标浅色（配深底），DARK = 图标深色（配浅底）
```

⚠️ **别再用 `setOverlaysWebView({overlay:true})` + `setBackgroundColor('#00000000')`**
（上一版就是这么写的，结果真机上报「一片白、状态栏那条也白、书还打不开」）：
Android 15 本来就强制 edge-to-edge，这两句会把 WebView 一起搞透明，
露出 Activity 的白底 —— **白屏和白条是同一个原因**。

当时的做法和踩的坑记在下面，留作备忘。

「上下」保持连续卷轴；「覆盖 / 平滑 / 仿真」切到**真分页**：位置由"第几页"决定，
不是由滚动量决定。底栏会显示「第 2 章 · 第 3 / 40 页」，两个键变成上一页 / 下一页，
左右滑和轻点屏幕左右三分之一也能翻页（点中间还是收放两条栏）。

**分页不是另一套 DOM。** 页边界是"段落粒度"的，所以做法只是在现有卷轴上量出
"每页的第一段是谁"，然后把视口顶边对准它。渲染、增量补段、窗口化、打开防卡、
进度/书签那几套全部白用 —— 这也是没选 CSS `columns` 的原因
（columns 要一次排完整章，正是 4.6.1 里那个卡死风险）。

```js
paged()        // 上下 = 滚轴；其余三种 = 分页
pageH()        // 一页多高 = 正文可视高 − 上下留白
scanTops(blk)  // 段落位置缓存（字号/行距/字体/页高/宽度一变就作废重扫）
computePages() // 切页：pages = [{s: 段索引, y: 相对章顶 px}]
ensurePages()  // 排到"至少 n+1 页"，分帧 + 时间预算
pageAbsTop()   // 第 n 页在卷轴里的绝对位置（现量现算）
```

#### 分页踩的四个坑（都是量出来的，功能撤了但值得记着）

1. **页首要减掉 `paddingTop`。** `scrollTop = S` 时内容坐标 c 的东西出现在 `c - S`
   处，要让页首段落在内容区顶部得 `S = c - padTop`。不减这个数，每页都往上顶 56px，
   第一页的章节标题直接缩到状态栏底下（测试量出来"页首偏移 −56px"）。
2. **切页要按段底判，不是段首。** 只看"段首越没越过页底"的话，一段从页尾前一点点
   开始、往下伸出大半段，页尾就溢出了。放不下就整段推到下一页。
3. **页尾还要一条遮罩。** 内容是一条连续长书页，页边界只决定"翻页跳到哪"，
   拦不住浏览器把下一页的第一段在页底排出来一小截（实测最后一行底 807、
   而内容区底只有 641）。所以加了 `#page-tail`：从"本页最后一段的下沿"盖到屏幕底，
   页尾变成干净的留白，跟纸质书一样。
4. **分页模式下两条栏必须一直摊开**（那里没有"滚动动作"，栏一收页码就看不见了），
   而且正文的上下留白要按**栏的真实高度**让位（量出来的，不是写死像素），
   否则页首被顶栏压掉一半、页尾被底栏吃掉。

#### ⚠️ 「翻页」这四个不是"分页"

本 App 现在是一条**连续的长书页**（4.6），没有"页"可翻。
所以这四个管的是**跳章时怎么过渡**（点上一章/下一章、拖进度条跳章）：

| 选项 | 实际行为 |
|---|---|
| 上下 | 直接跳（默认，最省） |
| 平滑 | rAF 推着 scrollTop 走一段 ease-out（老 WebView 没有 `scrollTo({behavior})`） |
| 覆盖 | 位置瞬间到位，**新的一屏**从屏幕下方滑上来把旧的一屏盖住（带点上缘阴影） |
| 仿真 | 同一对浮层，但新的一屏绕左边立起来翻一下再落平（`perspective + rotateY`，`transform-origin: left center`） |

**想要真的分页（一屏一屏翻）是另一件大事**，得先做"把一章按屏幕高度切页"。

#### ⭐ 动画对象是「一屏大小的浮层」，不是那条长卷轴

这一条是用一次**真机彻底卡死**换来的，千万别改回去。

第一版我给 `.chapter-block` 挂 `animation + perspective`：那一块在真机上可能是几千个
`<p>`、十几万像素高，浏览器为了做 3D 动画要把它整个提成合成层 ——
等于往显存里塞几百 MB 的纹理。后果是**连锁的**：

1. 跳章那一下先卡住；
2. 之后**再打开这本书**要重新排那一大块，直接卡死在「正在排版正文」，
   连看门狗的定时器都排不上队（主线程被独占）。

现在的做法是行业标准那套（`page-flip` / StPageFlip 的"克隆两页 + 层叠 z-index"，
以及掘金那篇《电子书阅读器之翻页模式》里的层叠 + 透视公式）：

```js
fxSnapshot()   // 把"此刻看得见的那几十个 <p>"克隆成一张跟屏幕一样大的浮层
moveTo(y)      // 覆盖/仿真：先拍旧的一屏 → 位置瞬间到位 → 新的一屏滑上来
```

三条硬规矩：

| 规矩 | 为什么 |
|---|---|
| 克隆出来的层要套一层 `.chapter-content` | 段的样式是 `.chapter-content p` 给的，离开原来的祖先就丢 |
| `.fx-stage` 铺满全屏但 `pointer-events: none` | 不写就会吃掉整屏点击（这个坑之前在速度面板上踩过一次） |
| 兜底 560ms 强拆浮层 | 连着跳两次时 `animationend` 可能不来，不拆就留一地脏层 |

浮层里永远只有几十个节点，跟章节多长无关 —— 这也是它不会再卡死的原因。

#### 平滑滚动踩的两个坑

1. **第一版点了没反应。** 跳章会顺手触发"补一章"，那一插要走 `preserve()` 补偿
   scrollTop；我原本在 `preserve()` 里直接把动画掐掉了 → 动画死在第一帧。
   改成让**目标跟着补偿一起挪**（`smoothTo += d`），动画每帧朝最新的 `smoothTo` 插值：

   ```js
   el.scrollTop = start + (smoothTo - start) * e;   // start 固定，目标取最新
   ```
2. **结尾抖一下。** 动画跑一半时 `trimBlocks` 卸载了远处的章节，卷轴长度变了，
   补偿把 scrollTop 拨回去、插值跟不上（实测 9106 → 4547 → 4700）。
   现在**动画期间不卸载**（`smoothTo === null && trimBlocks(snap)`），落定了再干。

顺带修了个真 bug：**连点两次「下一章」第二次会整条重画**（目标章没挂着 →
走 `renderStream`，屏幕闪一下）。现在跳完章就调 `ensureNeighbors()`
把前后邻居补上，两次都是滚过去。

- 面板宽 `78%`、**上限 440px**。原来上限写的 340px，在视口 500px 出头的机器上会被压到

上下箭头各翻一屏（0.9 × clientHeight），中间是滑轨 + 可拖的滑块。

#### 两条滑动条共用一个拖动器（`dragify`）

目录那个胶囊滚动条和底栏那根章节进度条，现在都走同一个 `dragify()`。
她报的"滑动卡顿 + 会卡死"，是**两个不同但都真实的原因**：

**① 卡顿 = 每个 pointermove 都逼浏览器重排一次。**
以前两条都是"每次 move 就读一次几何（`getBoundingClientRect` / `scrollHeight` /
`clientHeight` / `offsetHeight`）→ 写一次 DOM"。读几何会**强制浏览器立刻排版**，
而正文里几千个 `<p>`、目录里上千条 `.toc-item`，排一次好几毫秒；写完下一帧又读，
等于每个 move 触发两三次全文档排版 —— 手指一划每秒几十次，帧全掉在这儿。
目录那条更狠：写 `list.scrollTop` 会触发 `scroll` → `syncTocBar` 又读四个几何量，
一轮拖动能排两次版。

修法两条：

- **只在手指按下时量一次几何**（`ops.measure()`），整段拖动用缓存；
- 用 rAF 合并写入，一帧最多写一次 DOM。

实测拖动期间 **63–65 fps**（满帧）。

**② "卡死" = `pointerup` 不来，`dragging` 永远是 true。**
WebView 里切后台、被系统手势接管、长按后系统把指针收走，`pointerup` 都可能根本不派发。
那时闭包里的 `dragging` 一直是 true，**之后手指在屏幕上随便动一下都在"拖"**，
看着就是卡死 / 乱跳。现在三道保险：

| 保险 | 说明 |
|---|---|
| `pointerup` / `pointercancel` | 正常路径 |
| `visibilitychange` / `pagehide` | 页面被盖住或退后台，一定收尾 |
| **3 秒没有任何事件就当松手** | 最后一道，专治"up 丢了" |
| `setPointerCapture`（有就用） | 手指滑出滑块范围也能继续收到后续事件 |

`?act=drag` 里专门有一条"**故意不发 pointerup**"的测试：
按下 → 拖 → 等 3.3 秒 → 再乱动手指，断言滑块**没有跟着跑**（相等即通过）。

### 4.14 全屏沉浸 + 边缘贴合

**系统状态栏和导航栏要一起藏。** `@capacitor/status-bar` 只管状态栏，
底部那条系统导航栏它碰不到 —— 所以自己写了个几十行的原生插件
`android/app/src/main/java/com/yuanchuan/yandu/ImmersivePlugin.java`：

| 方法 | 干什么 |
|---|---|
| `hide()` / `show()` | `WindowInsetsController.hide/show(Type.systemBars())`，两条一起 |
| `insets()` | 把系统栏的**真实高度**量出来（px）给 JS |

用的是 `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`：藏了以后从屏幕边缘滑一下
能临时唤出系统栏、滑完自己收回 —— 不会把人锁死在里头。

⚠️ `registerPlugin(ImmersivePlugin.class)` 必须写在 `MainActivity.onCreate`
里 `super.onCreate()` **之前**，顺序反了插件不生效，而且 JS 那边只拿到
`undefined`（静默失效，很难查）。

**边缘贴合**：以前 `--safeT` 写死 46px、`--safeB` 写死 26px，
各家机器的刘海/挖孔/手势条高度都不一样，写死必然对不齐。现在启动时调一次
`insets()` 把真值写进这两个变量；**全屏沉浸时直接归 0**，顶栏底栏就贴到物理边界上。
上下两条栏自己也不再额外补空白（顶栏 `safeT + 42`、底栏 `padding-bottom: safeB`）。

**测的时候别用 `getBoundingClientRect` 判"贴底"**：栏收起时带
`transform: translateY(100%)`，rect 会整个挪到屏幕外（量出来比阅读页底还低一截，
看着像 bug，其实是对的）。用 `offsetTop + offsetHeight`——那是布局位置，不受 transform 影响。

### 4.15 自动翻页（可调速的匀速滚动）

设置面板第四行左边的「自动翻页」= **匀速往下滚**，不再跟「章节连续阅读」
（读完一章自动接下一章，在"更多阅读设置"里）共用开关 —— 之前共用的时候
按下去根本看不出干了什么。

- 速度：数值 **×4 = 每秒滚多少像素**。19 ≈ 76px/s，一屏约 10 秒。范围 5–60。
- 引擎是 `autoTick()` 的 rAF 循环，按 `dt` 累加，`dt > 400ms`（切后台回来）直接跳过那一帧。
- **人一滑就让位**：滚动回调里靠 `state.autoStep` 标记区分"是它推的还是人滑的"，
  人滑的就把 `autoPauseUntil` 推到 1.2 秒后 —— 不然两边对着拽。
- 到底了先试 `nextChapter()`，接不上就是真读完 → 停下并提示。
- 离开阅读页自动停（`showPage` 里）。

**开着的时候面板是收起来的**（她明确要求："点了之后设置面板和速度面板都收掉，
要调的时候再点才出来"）：

| 动作 | 结果 |
|---|---|
| 点「自动翻页」那一行 | 开起来，**设置面板和速度面板都收掉**，右下角出现一枚小胶囊「自动 19 ›」 |
| 轻点正文 | 速度面板弹出来；再轻点收回去（自动翻页开着时，轻点专门管这件事） |
| 点右下角小胶囊 | 同上（两条栏摊开时才看得到它） |
| 再点设置里那一行 | 也是叫出速度面板（关掉是面板里那个「退出自动翻页」的活） |

**速度面板**（`#sheet-speed`）就是她给的规格：第一行 手写风「速度」+ 胶囊「减速 -」+
数值 + 胶囊「加速 +」，第二行一条微弱细线隔开 + 一个横跨大半屏的「退出自动翻页」。
配色**跟亮度面板同一套**（`var(--panel)` + 主题字色/描边）—— 第一版我写死了深色
`#17181a`，夜间/青灰主题下跟别的面板完全不是一个调子，她说得对。
手写风用楷体字体栈（`"Kaiti SC", "STKaiti", KaiTi, "楷体", cursive`）——
安卓上没装楷体会回落到系统字体，这个没法强求。

⚠️ `.sheet` 容器是铺满全屏的，一显示就吃掉整屏点击（表现："开了自动翻页之后
哪儿都点不动、面板也关不掉"）。所以速度面板的容器 `pointer-events: none`，
只有面板本体 `auto` —— 以后做"不挡背景"的浮层都得这么写。

### 4.16 ⚠️ `--dump-dom` 那个测试方法在某些功能上会骗人

自动翻页第一次测出来"完全没生效"，查了两轮才发现是**测试方法假**：
`--virtual-time-budget` 会压缩 `setTimeout`，但几乎不推进 `requestAnimationFrame`
——整个测试只跑了 2、3 帧，而滚动节流、增量渲染全是 rAF 驱动的，等于什么都没执行。

判断方法：在页面里放一个计数器 `requestAnimationFrame(()=>cnt++)`，
测完把 `cnt` 打出来。只有个位数就说明这一轮跑的结果不可信。

所以有了 `tools/cdp-run.js`（CDP 直连，真等真滚）：

```bash
node tools/cdp-run.js "file:///.../design/phone-sim.html?act=autonext" 9000
SHOT=out.png node tools/cdp-run.js "file:///.../design/phone-sim.html?act=continue" 6000
```

它用 `Target.createTarget` + `Page.navigate` + 真实 `sleep()`，
还能把 `Runtime.exceptionThrown` 收集出来。凡是跟**滚动 / 动画 / 定时器**有关的验证都走它，
`--dump-dom` 只留给"点一下看 DOM 结构"这类静态检查。

### 4.17 ⚠️ 阅读页整页僵住：`afterConnect` 的微任务死循环

**症状**：打开一本书，页面完全不动 —— 不是慢，是**彻底卡住**：`setTimeout`、
`requestAnimationFrame`、绘制、CDP 的 `Runtime.evaluate` 全都没反应。
用 `?case=big` 那本"一章 20000 段"的天书反而测不出来（那条路是同步排版太重，
遮罩收得慢但会动），能触发它的是**相反的另一种书：短章合集**——
一整本一屏装得下好几章（诗集、微章节网文就是这样）。

**链路**（三个条件同时成立才会成环）：

```
maybeConnect() 条件成立 → loadChapter(idx+1)
   → 这一章「已经在飞」→ return Promise.resolve(null)      ← 已兑现的微任务
   → .then(afterConnect) → afterConnect 同步跑 maintain()
   → maintain() 里再 maybeConnect() → 几何一个字都没变 → 条件还成立 → 回到第 2 行
```

微任务队列永远排不空，**事件循环一步都走不出去**，所以 IndexedDB 那个真回调
永远挤不进来 —— 死锁就是这么来的。实测每秒 20 万次 `getBoundingClientRect`，
全部来自 `snapshot()`，而且**一次 DOM 增删都没有**，这个"只读不写"的形状就是它的指纹。

**修了三处**：

| 改动 | 挡的是什么 |
|---|---|
| `loadChapter(...).then(afterAppend)`，`afterAppend(blk)` 只在**真拿到块**时才续 | 断掉那条空链：去重返回的 `null` 不该再触发一轮维护 |
| `afterConnect()` 改成"一帧最多排一次"（`afterQueued`） | 就算哪天又成环，也只是每帧一次，饿不死事件循环 |
| `maybeConnect()` 两个分支各加 `!findBlock(目标章)` | `ensureNeighbors()` 一直有这道判重，只有这里漏了 |

**怎么在"主线程完全不响应"的情况下定位**（这次真正有用的招）：
`Debugger.pause` 和 `Runtime.evaluate` 都要靠那条被占死的线程，等于没用。
改成在页面加载**之前**用 `Page.addScriptToEvaluateOnNewDocument` 注入一层壳，
给 `appendChild` / `getBoundingClientRect` / `offsetHeight` / `scrollTop` 的 setter 计数，
每 400 次把统计写进 `document.title` —— **标题是浏览器进程侧的**，
于是从外面 `GET /json/list` 就能读到活的热点调用链：

```
T188400|94184:gbcr←snapshot(...) ; 47095:scrollHeight←snapshot(...) ; 47088:offsetHeight←estFullHeight(...)
```

一行就把嫌疑收到"几何读 + estFullHeight"上，也就是 `maintain/maybeConnect` 那条链。
（顺带一个坑：那层壳里**别把 `appendChild` 变成空转来"掐断"循环** —— 那样会自己造出一个
假死循环，把诊断带偏；数了就让它照常执行。）

### 4.18 程序化滚动 vs 人手滑：记"上一次写进去的值"，别记时间窗

`scroll` 回调里得把"人一滑"和"我们自己写的 `scrollTop`"分开：前者要让自动翻页让位
（`autoPauseUntil = now + 1200`），后者不该。
原来只有一个 `state.autoStep`，**只有 `autoTick` 那一处会置位**，
而写 `scrollTop` 的地方一共有五处（自动翻页推进、`preserve()` 的视线补偿、
`applyPendingTop()` 落位、`moveTo()` 跳章、`smoothScrollTo()` 每帧插值）——
漏掉的那四处每次都被判成"人滑了"，自动翻页于是每接一次章就自己停 1.2 秒。

**第一版我改成「打时间戳 + 判 150ms 之内」，是错的**：自动翻页每 16ms 就写一次 `scrollTop`，
时间窗被它自己一路续期，真人的滑动反而永远识别不出来 —— 等于把「让位」整个废掉，
比原来那个毛病还难受。是 `tools/selftest-cases.js` 的 C6 **控制组**照出来的
（人在滑，`autoPaused` 却不亮）。现在的判法两条腿：

| 信号 | 怎么用 |
|---|---|
| `markProgScroll()` 在**每次写完 `scrollTop` 之后**回读一次，把值记进 `progTop` | 事件到来时当前位置还等于 `progTop`（±2px）= 我们自己动的；差出去了 = 别人（人）挪的。写完才回读，是因为越界的目标值会被浏览器夹住，只有回读才是真落点 |
| `#reader-body` 的 `touchstart` 里直接给让位 | 手指按下去是**最确定不过**的「人在动」，不该拿去和每帧的自动推进抢归因 |

⚠️ 顺带一条测试规矩：**只验「不该发生」的断言必须配控制组**。
C6 原来只写「没人滑的时候 `autoPaused` 要为 false」，而自动翻页关着时那个字段恒为 false ——
是个空断言，怎么测都绿。补上「手指按下之后要为 true」，它才第一次真的红过。

调试入口 `window.__reader()` 现在多带两个只读字段：`autoNext`、`autoPaused`
（原有那些不动）—— 判"没人在滑的时候不该进让位暂停"这类断言只能从这里取，
别为了测试去改状态。

## 5. 环境备注

- JDK 21（`JAVA_HOME` 指向 `C:\Program Files\Java\jdk-21`）
- Android SDK 装在 `D:\Android\Sdk`，需设置 `ANDROID_HOME` / `ANDROID_SDK_ROOT`
- 新版 cmdline-tools 已弃用 `sdkmanager`，改用 `android.exe sdk install`
- 通过 `cmd /c sdkmanager.bat` 传包名时，分号会被批处理当参数分隔符拆开，
  导致 `platforms;android-35` 装不上，必须直接调 `android.exe` 走 argv
- `tools/fixtures/gbk.txt` 是**真 GBK 字节**（`iconv -f UTF-8 -t GBK` 生成，598 字节，
  反读能还原成那段中文）。别用编辑器打开它再"另存为"—— 存成 UTF-8 之后
  编码探测那条用例（C1）就永远测不到 GBK 这条路了。`.gitattributes` 里已按 binary 登记。
- 连着跑两轮 `tools/cdp-run.js` 要给**不同的 `CDP_PORT`**：上一轮的 headless Edge
  没退干净会顶着 9333，下一轮的 `waitPort` 连到那个旧实例上，然后一路卡住不返回
  （这坑在脚本注释里写着，这次真踩到了）。跑之前可以确认一下端口是空的。
- 行尾由 `.gitattributes` 钉住：`.bat` 走 CRLF、`gradlew` 走 LF、图片/apk/GBK 夹具按二进制。
  这台 Windows 上少了这一份，`android/gradlew.bat` 和编码夹具都会出莫名其妙的毛病。
